사용자가 지정한 기능 또는 최근 변경사항을 분석해서 `docs/` 경로에 상세 기능 명세 MD 파일을 생성해줘.

사용자 입력: $ARGUMENTS

## 분석 대상 결정

**`$ARGUMENTS`가 있는 경우**:
- 파일 경로(예: `src/controller/UserController.java`)면 해당 파일 및 연관 파일(Service, DAO, Mapper, XML 등) 탐색
- 키워드(예: `user-auth`, `payment`)면 `src/` 내 관련 파일을 Grep/Glob으로 검색
- 찾은 파일들을 직접 읽어 구현 내용 분석

**`$ARGUMENTS`가 없는 경우**:
- `git diff HEAD~1 HEAD`로 최근 커밋 변경사항 파악
- 변경된 파일들을 직접 읽어 구현 내용 분석
- diff가 없거나 너무 작으면 사용자에게 기능명을 물어볼 것

어느 경우든 코드를 **직접 읽어** 작성. 추측 금지.

## 파일명 규칙

- **반드시 기능 도메인별 하위 폴더에 생성**: `docs/auth/`, `docs/payment/`, `docs/user/`, `docs/notification/` 등
- 폴더명은 기능의 핵심 도메인을 kebab-case로: `docs/api-usage-log/` 보다는 `docs/apikey/`처럼 간결하게
- 파일명은 kebab-case: `login-flow.md`, `payment-webhook.md`
- 반복 업데이트되는 기능(개선 이력이 있는 경우)은 날짜 prefix 추가: `YYYYMMDD-기능명.md`
- 단, 프로젝트 전반에 걸친 공통 기능(인증, 보안 필터 등)만 `docs/` 루트에 생성 허용

## 문서 작성 기준

**작성 언어**: 한국어

**포함해야 할 섹션** (해당되는 항목만):

### 필수
- `## 개요` — 기능 목적, 적용 범위, 핵심 동작 1~2문장 요약
- `## 관련 파일` — Controller/Service/DAO/Mapper/XML/Template 등 관련 파일 표로 정리

### 해당 시 포함
- `## 엔드포인트` — URL, 메서드, 요청 파라미터 표, 요청 예시
- `## 응답 구조` — JSON 예시 + 필드 상세 표
- `## DB 구조` — 테이블 컬럼 표 + DDL SQL
- `## 처리 흐름` / `## 검증 흐름` — ASCII 다이어그램으로 단계별 흐름 표현
- `## 검색 처리 로직` — 단계별 알고리즘, 정규식, 분기 조건 상세 설명
- `## 주요 설계 결정` — 왜 이렇게 구현했는지 배경과 트레이드오프
- `## 에러 코드` — 코드/HTTP상태/메시지/발생조건 표
- `## 알려진 제약 사항` — 미구현 기능, 엣지케이스, 한계점

## 작성 스타일

- 표(Table)를 적극 활용: 파라미터, 필드 설명, 에러 코드 등
- ASCII 플로우차트로 처리 흐름 시각화
- SQL 쿼리는 핵심 조건 위주로 코드블록에 포함
- 설계 결정에는 **이유**를 반드시 명시 (단순 "이렇게 했다"가 아닌 "왜")
- 실제 예시 데이터로 동작 검증 가능하게 작성
- 코드에서 읽은 내용 기준으로 충분한 상세도를 목표로

## 주의사항

- 코드에서 직접 읽어서 작성 (추측 금지 — 실제 구현과 다른 내용 작성 금지)
- 구현이 미완성인 부분은 `## 알려진 제약 사항`에 명시
- `docs/` 폴더가 없으면 자동으로 생성 후 진행
- 파일만 생성하고 커밋 여부는 사용자가 결정
