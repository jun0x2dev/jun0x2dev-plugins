사용자가 지정한 기능 또는 최근 변경사항을 분석해서 `docs/` 경로에 상세 기능 명세 MD 파일을 생성해줘. 작성 후에는 반드시 문서를 코드와 다시 대조 검증하고, 불일치가 있으면 바로 고쳐줘.

사용자 입력: $ARGUMENTS

## Phase 1: 분석 대상 결정

**`$ARGUMENTS`가 있는 경우**:
- 파일 경로(예: `src/controller/UserController.java`)면 해당 파일 및 연관 파일(Service, DAO, Mapper, XML 등) 탐색
- 키워드(예: `user-auth`, `payment`)면 `src/` 내 관련 파일을 Grep/Glob으로 검색
- 찾은 파일들을 직접 읽어 구현 내용 분석

**`$ARGUMENTS`가 없는 경우**:
- `git diff HEAD~1 HEAD`로 최근 커밋 변경사항 파악
- 변경된 파일들을 직접 읽어 구현 내용 분석
- diff가 없거나 너무 작으면 사용자에게 기능명을 물어볼 것

어느 경우든 코드를 **직접 읽어** 작성. 추측 금지.

## Phase 2: 템플릿 선택

분석 대상의 성격에 따라 아래 두 템플릿 중 하나를 고른다. 애매하면 사용자에게 물어본다.

- **사양서형** — "이 기능이 지금 어떻게 동작하는가"를 정리하는 경우 (신규 기능, 기존 기능 전체 분석, 리팩터링 후 최신 구조 정리 등)
- **변경이력형** — "이번에 뭘 왜 고쳤는가"를 남기는 경우 (버그 수정, 특정 이슈 대응, `$ARGUMENTS` 없이 최근 diff 기반으로 문서화하는 경우)

## 파일명 규칙

- **반드시 기능 도메인별 하위 폴더에 생성**: `docs/auth/`, `docs/payment/`, `docs/user/`, `docs/notification/` 등
- 폴더명은 기능의 핵심 도메인을 kebab-case로: `docs/api-usage-log/` 보다는 `docs/apikey/`처럼 간결하게
- 파일명은 kebab-case: `login-flow.md`, `payment-webhook.md`
- 반복 업데이트되는 기능(개선 이력이 있는 경우)은 날짜 prefix 추가: `YYYYMMDD-기능명.md`
- 단, 프로젝트 전반에 걸친 공통 기능(인증, 보안 필터 등)만 `docs/` 루트에 생성 허용

## Phase 3: 문서 작성

**작성 언어**: 한국어

### 사양서형 섹션 구성

**필수**
- `## 개요` — 기능 목적, 적용 범위, 핵심 동작 1~2문장 요약. 곧바로 이어서 **요약** 소단락(bullet 4~6개)으로 입력→처리→출력 흐름을 한눈에 볼 수 있게 압축
- `## 관련 파일` — Controller/Service/DAO/Mapper/XML/Template/프론트 등 관련 파일 표로 정리

**해당 시 포함**
- `## 엔드포인트` — URL, 메서드, 요청 파라미터 표(파라미터/위치/필수/타입/설명), 요청 예시
- `## 응답 구조` — JSON 예시 + 그룹별 소제목(`###`)으로 나눈 필드 상세 표
- `## 처리 흐름` — ASCII 다이어그램으로 단계별 흐름, 분기 조건, 실패 시 동작까지 표현
- `## 사용 테이블` — 테이블별 스키마/역할/매칭 키(조인 조건) 표. DB를 쓰는 기능이면 인덱스 현황 하위 표도 포함(아래 "DB 스키마 검증" 참고)
- `## 핵심 SQL` — 가장 복잡하거나 중요한 쿼리 원문 + 왜 이렇게 짰는지 이유
- `## 검색 처리 로직` — SQL 대신 알고리즘/정규식/분기 조건이 핵심인 기능일 때
- `## 응답 코드` / `## 에러 코드` — 코드/HTTP상태/메시지/발생조건 표
- `## 알려진 제약 사항` — 미구현 기능, 엣지케이스, 한계점
- `## 히스토리` — 최초 구현 → 이후 확장 순서로 한 줄씩 (반복 업데이트되는 기능일 때)

### 변경이력형 섹션 구성

**필수**
- `## 개요` — 무엇을 왜 고쳤는지 1~2문장
- `## 무엇이 문제였나` — 증상 + 원인을 코드 근거와 함께 (재현 예시가 있으면 포함)
- `## 어떻게 수정했나` — 수정 내용을 표로 정리 (# / 수정 / 효과)
- `## 관련 파일` — 레이어/파일/변경 내용 표

**해당 시 포함**
- `## 주요 설계 결정` — 왜 이 방식을 택했는지, 배제한 대안과 이유
- `## 동작 결과` — 실제 검증한 케이스 목록 (가능하면 실행 결과 근거)
- `## 알려진 제약 사항`

## 작성 스타일

- 표(Table)를 적극 활용: 파라미터, 필드 설명, 에러 코드, 사용 테이블 등
- ASCII 플로우차트로 처리 흐름 시각화
- SQL 쿼리는 핵심 조건 위주로 코드블록에 포함
- 설계 결정에는 **이유**를 반드시 명시 (단순 "이렇게 했다"가 아닌 "왜")
- 실제 예시 데이터로 동작 검증 가능하게 작성
- 코드에서 읽은 내용 기준으로 충분한 상세도를 목표로
- 요청하지 않은 부가 섹션(스펙 문서와의 차이 이력, 프론트 UI 상세 등)은 먼저 넣지 말고, 필요하면 사용자에게 추가할지 물어본다

## Phase 4: 검증

문서를 다 쓴 뒤, **Phase 1~3에서 파악한 내용을 그대로 믿지 말고 관련 소스 파일을 다시 Read해서** 문서에 적은 사실을 하나씩 대조한다. 대상:

- 엔드포인트 URL/HTTP 메서드가 `@RequestMapping`/`@GetMapping` 등과 일치하는가
- 요청 파라미터명·필수 여부·타입이 실제 파라미터 선언과 일치하는가
- 응답 필드명·타입·설명이 실제 DTO/`@Schema`와 일치하는가
- SQL 조건·조인·컬럼명이 Mapper XML 원문과 일치하는가 (문서에 발췌한 SQL은 원문 그대로여야 함)
- 분기 조건(에러 코드가 발생하는 조건 등)이 서비스 로직과 일치하는가
- 문서에 인용한 파일 경로가 실제로 존재하는가

**DB 스키마 검증**: 프로젝트에 DB를 직접 조회할 수 있는 도구(MCP 등)가 연결돼 있으면 활용해 테이블/컬럼/인덱스 존재 여부까지 확인한다. 그런 도구가 없으면 DDL 파일이나 코드에 있는 근거로만 검증하고, 확인 불가능한 내용(예: 실제 인덱스 존재 여부)은 **추측해서 단정하지 말고** 문서에 "코드 기준으로는 확인 불가" 정도로 남기거나 해당 서술 자체를 생략한다.

발견한 불일치는 **바로 문서를 수정**한다(사용자에게 먼저 물어보지 않음 — 검증 대상이 방금 작성한 문서 자체이고, 판단이 아니라 사실 대조이므로). 수정 후 아래 형식으로 짧게 보고한다:

```
## 검증 결과
- 확인함: N건
- 수정함: N건
  - <무엇을 어떻게 고쳤는지 한 줄씩>
- 확인 불가(DB 도구 없음 등): N건
```

불일치가 하나도 없으면 "검증 완료 — 불일치 없음"으로 간단히 종료한다.

## 주의사항

- 코드에서 직접 읽어서 작성 (추측 금지 — 실제 구현과 다른 내용 작성 금지)
- 구현이 미완성인 부분은 `## 알려진 제약 사항`에 명시
- `docs/` 폴더가 없으면 자동으로 생성 후 진행
- 파일만 생성/수정하고 커밋 여부는 사용자가 결정
